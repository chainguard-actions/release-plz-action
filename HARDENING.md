## Findings Fixed

### script-injection (severity: high)

Sub-rule (a): Multiple `${{ inputs.* }}` expressions are interpolated directly inside `run:` shell command strings in two steps of action.yml. In the 'Install release-plz' step, `${{ inputs.version }}` is embedded directly in the cargo-binstall command line. In the 'Run release-plz' step, the following inputs are all interpolated directly into shell code: `${{ inputs.config }}`, `${{ inputs.verbose }}`, `${{ inputs.dry_run }}`, `${{ inputs.token }}`, `${{ inputs.forge }}`, `${{ inputs.backend }}`, `${{ inputs.registry }}`, `${{ inputs.manifest_path }}`, `${{ inputs.project_manifest }}`, and `${{ inputs.command }}`. An attacker who controls these inputs (e.g. via `workflow_dispatch` or by calling this composite action from a malicious workflow) can inject arbitrary shell commands. All these values must be moved to `env:` variables and referenced as quoted `"$VAR"` shell variables instead.

### github-env-injection (severity: high)

The 'Run release-plz' step writes multiple values to `$GITHUB_OUTPUT` without the required sanitization (`printf '%s' ... | tr -d '\n\r'`). The values written — `prs`, `pr`, `prs_created`, `releases`, `releases_created` — are derived from tool output that was produced using attacker-controlled inputs (e.g. `${{ inputs.command }}`, `${{ inputs.config }}`, etc.). A malicious input could cause the tool to emit newline characters in its JSON output, allowing injection of arbitrary key=value pairs into `$GITHUB_OUTPUT`, which could poison downstream step outputs. Each write (e.g. `echo "prs=$prs" >> "$GITHUB_OUTPUT"`) must be preceded by sanitization: `safe=$(printf '%s' "$prs" | tr -d '\n\r')` before writing.
